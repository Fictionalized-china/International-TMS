## 统一业务模型

本次按一套总逻辑收口，不再以页面或岗位各自维护一套状态：

1. `SO` 是客户商业订单，承载客户、委托、费用、责任人和最终结算。
2. `OUL` 是可扫码、可入库、可包装、可装车、可追踪的实物单元。
3. `PZ` 是运输批次/配载单；同一订单可把不同 OUL 分配到多张 PZ，多批并行运输。
4. 同一 OUL 不得同时进入两个有效运输批次或装车任务；取消只释放本批 OUL。
5. 订单级节点按全部 OUL 聚合：任一批次未完成时保持“分批运输中”，不得把整票提前推进到签收、结算或归档。
6. 全部 OUL 到仓、客户签收、应收应付签核、账单、收付款和核销均完成后，才允许最终复盘归档。
7. 老板账号可代办全部岗位，但仍受资料必填、状态顺序、库存、费用、核销和审计门禁约束；普通岗位继续按数据范围和权限隔离。

## 本次交付范围

- 录单红字必填与后续节点提交门禁统一，缺项可明确查看并返回原入口补齐。
- 操作主管审核时可查看完整委托、货物、路线、口岸、责任人和应收应付信息。
- 仓库收货、包装、出库、境外到仓及签收事实按 OUL 保存；现场照片与客户可见范围沿用配置策略。
- 同一订单多批运输、PZ-OUL 映射、批次独占、分批装车、批次运踪、境外收货和订单级聚合完成。
- 费用分摊按批次实际 OUL、重量/体积及冻结依据执行，保留人工调整和审计，不重复生成订单级费用。
- 已审批关键资料采用受控更正和重审，禁止直接覆盖已发生的实物、运输、费用或资金事实。
- 老板单账号完整流程与原岗位协作流程同时保留。

## 业务操作顺序

业务员/老板录单 → 操作主管审核分配 → 国内提货与仓库收货 → 生成/确认 OUL → 操作主管按 OUL 生成一张或多张 PZ → 商务落实车辆资源 → 操作主管确认 → 仓库按批装车出库 → 单证/报关/运踪按批办理 → 境外仓按批收货 → 全部 OUL 到仓后客户签收 → 客服/操作/操作主管/财务完成应收应付签核 → 生成并确认账单 → 出纳登记收付款并核销 → 财务复盘归档。

岗位可以协作办理；老板也可以在不跳过门禁的前提下独立走完整流程。
