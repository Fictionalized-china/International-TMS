## 已实现的安全边界

1. 管理后台登录必须存在启用的非仓库角色。仓库专用账号和客户账号不能从 `/login` 进入管理后台。
2. 仓库端登录必须有仓库查看权限和明确的仓库绑定。登录后自动进入该账号绑定的仓库，不再显示“选择测试仓库账号”，也不接受前端传入仓库编号来切换仓库。
3. 客户门户账号没有启用的组织成员关系，不会获得管理后台或仓库端会话。
4. 每个正式账号只保留蓝图规定的一个岗位角色；个人权限覆盖被清空，避免历史权限残留。
5. 每个角色的权限积木在初始化时重置为代码中的基线，避免已有环境出现“同名角色但权限不同”。老板角色重新取得全部权限。
6. 所有旧会话在初始化前后都会撤销，避免账号停用后已有 Cookie 继续访问。
7. 没有业务权限的商务报价岗和前端配载岗仍可正常登录，但只看到岗位归类说明，不会因 403 崩溃，也不会看到订单数据。
8. 报价、销售、配载单、文件中心、文件直链、货物列表和货物图片均在服务端按账号的数据范围过滤；不能通过修改 URL、文件编号或批次编号绕过页面权限读取其他人员数据。
9. 旧版会话或异常会话缺少角色字段时按“无特权”安全降级，不会因为权限数据不完整导致页面崩溃或被误判为老板权限。

## 初始化与回滚策略

- 生成命令：`npm run accounts:prepare -- --organization-code <正式组织代码>`；组织代码必须显式提供，避免误写入其他组织。
- 隔离复核命令：`npm run accounts:audit`
- 云端初始化 SQL：`.local-secrets/aliyun-production-accounts.sql`
- 云端审计 SQL：`.local-secrets/aliyun-production-access-audit.sql`
- 桌面账密本：`International-TMS-阿里云测试账密.md`
- `.local-secrets/` 已加入 `.gitignore`，禁止提交。
- 初始化 SQL 只能在数据库迁移全部完成、目标组织已经通过 `/setup` 创建后执行。
- 上线前必须先做数据库快照；若审计不通过，不开放公网登录。

## 阿里云部署边界

当前项目以 Cloudflare Workers 作为运行时，并通过 Wrangler 的 `DB` 环境绑定直接调用 Cloudflare D1。D1 官方文档说明，应用通过 Worker 的 `env.DB` 绑定访问数据库。因此现有产物不能被当作普通 Node.js 网站直接复制到阿里云 ECS 后运行。

如果要求应用和数据都在阿里云，需要在发布前完成以下适配：

1. 确定运行载体：优先建议 Linux ECS + 容器，或 SAE 镜像部署。
2. 把 Worker 请求入口适配为阿里云可运行的 Node/容器服务入口。
3. 把 D1 数据访问层迁移为阿里云可持久化的数据库方案，并完成 SQL 方言、事务、备份和恢复验证。
4. 配置 HTTPS、域名、日志、监控、备份、安全组和最小权限部署身份。
5. 迁移数据库结构后执行账号初始化 SQL，再执行审计 SQL；全部为零异常才开放登录。

如果只把域名或 DNS 放在阿里云，而应用仍部署在 Cloudflare Workers/D1，则改动最小，但这不属于“系统和数据部署在阿里云”。该路线必须由项目负责人明确确认，不能默认替代真正的阿里云部署。

官方依据：

- Cloudflare D1 Worker 绑定：<https://developers.cloudflare.com/d1/worker-api/d1-database/>
- 阿里云 ECS Node.js 环境：<https://help.aliyun.com/zh/ecs/user-guide/quick-deployment-of-node-js-environment>
- 阿里云 SAE 镜像部署：<https://help.aliyun.com/zh/sae/how-to-deploy-code-mongo-nacos-and-seata-server-to-sae>

1. 阿里云控制台“资源”页截图，能看清已购买的产品名称、地域和资源状态；敏感编号可局部打码。
2. 如果已有 ECS：实例操作系统、公网 IP 或弹性公网 IP、SSH 用户名、SSH 私钥文件在本机的路径。不要发送阿里云密码、短信验证码或私钥正文。
3. 是否要求应用和数据库都必须位于阿里云。如果是，需要确认使用 ECS/SAE 和数据库方案；如果不是，需要书面确认可继续使用 Cloudflare Workers/D1。
4. 域名及备案状态；没有域名时可先使用临时地址做内部验收。
5. 正式组织名称与组织代码。当前初始化产物暂按本地验证组织代码 `e2e` 生成；收到正式代码后必须在发布前重新生成并再次隔离审计。
6. 预计同时在线人数、可接受的维护窗口，以及是否允许发布过程中短暂停机。
