# 订单全链路总体逻辑与实现收口

日期：2026-11-19
状态：本地开发收口基线；不推送 Git、不部署云端、不调整内网。

## 一、设计目标

系统只保留一张商业订单作为客户、委托、报价、费用、结算和归档主体；同一订单允许按实际包裹分多批运输，但不拆成多张商业订单。所有页面、按钮和自动同步都必须服从同一状态机，不能各自推断一套“已完成”。

总体链路：

`录单草稿 → 提交审核 → 审核分配 → 国内提货/入仓 → 包装成 OUL → OUL 分批配载成 PZ → 分批装车/报关/运踪/境外到仓 → 整单客户提货或签收 → 对账签核 → 收付款登记与核销 → 复盘归档`

## 二、四层业务模型

### 1. 商业订单层（SO）

- 一张 SO 代表一项客户委托，是客户、报价商务、应收应付、责任人、委托资料、结算和复盘的唯一主体。
- 拼车和整车都沿用 SO；整车可以只有一个运输批次，拼车及项目货可以有多个运输批次。
- SO 不因分批发运而复制，也不把某一批次的完成误当成整票完成。

### 2. 仓储实物层（入仓唛头 / OUL）

- 入仓唛头用于计划收货；仓库按实际扫描累计收货，未扫描部分继续待收。
- 二次包装形成 OUL。OUL 是运输独占、装车、出库、境外收货和现场照片的最小物理单元。
- 作废或已被有效 OUL 替代的来源包装不再重复计入可用库存；历史仍可追溯。

### 3. 运输批次层（PZ）

- PZ 通过 `transport_batch_packages` 绑定本批实际承运的 OUL。
- 同一 OUL 同一时刻只能进入一个活动 PZ 或活动装车任务；取消只释放本批 OUL，不影响其他批次。
- 装车、舱单、报关、运踪、境外到仓及批次成本均读取本批 OUL，不能复制整票重量、体积或包数。
- 一张 SO 可以同时存在“已到仓批次、在途批次、待配载 OUL”；页面必须分别展示，订单汇总显示“分批运输中”。

### 4. 资金与归档层

- 应收、应付、分摊、对账单、收付款流水和核销都归属于 SO，并保留费用方向、往来单位和来源批次的证据。
- 配载成本按本批实际 OUL 的约定权重分摊，整数分合计必须等于批次总成本，不能产生负尾差。
- 某一运输批次到仓不开放整票结算完成；只有全部有效 OUL 已完成运输，订单级物理模块才可完成。
- 只有必需模块全部完成、必填字段完整、应收应付签核完成、应收应付均已登记并足额核销，才允许复盘归档。

## 三、统一状态推进规则

### 1. 向前推进

每个向前写入口在同一提交时重新核对：

1. 当前账号仍有效、组织和岗位仍有效、具备当前动作权限；
2. 当前订单责任归属、任务处理人和工作流节点没有被其他窗口改变；
3. 本订单冻结的录单规则和当前必填字段均完整；
4. 当前动作依赖的上游物理、费用或审批事实已经完成；
5. 幂等请求没有被处理过；
6. 条件更新成功后才写审计、通知和派生同步任务。

任何一项失败都不得部分写入，不得靠前端隐藏按钮代替服务端门禁。

### 2. 聚合完成

- 批次完成只更新该 PZ/OUL 的事实。
- 订单物理完成由全部有效 OUL 聚合计算，不能由最后一次页面操作直接指定。
- 资金完成由账单、流水与核销事实聚合计算，不能由订单状态反推。
- 工作流投影允许重试，但重试只能重算派生状态，不能重复收货、出库、照片、费用或资金流水。

### 3. 更正与异常

- 草稿阶段可直接修正未冻结资料；审批后关键资料使用“申请更正 → 本单审核岗位复核 → 原子应用”。
- 已发生仓储或运输事实的字段不能静默倒改；实物差异走仓库异常，批次资源变化走配载/装车调整。
- 更正申请保存前后快照、依据、处理人和版本；源资料或作业状态已变化时，旧申请不能覆盖新事实。
- 已完成或已取消订单不能应用新的关键更正，但允许撤回或驳回未结束申请，避免僵尸待办。

## 四、岗位协作与老板单人模式

- 业务/客服：录单、客户资料和应收信息；记录独立报价商务。
- 操作：补充及维护履约资料、应收应付；查看完整委托。
- 操作主管：审核订单和双向费用、分配任务、创建配载计划并确认资源。
- 商务报价：根据配载需求找车并登记运输资源，不绕过配载计划直接生成运输事实。
- 国内/境外仓：只在所属物理仓范围办理扫描、收货、包装、装车、出库、境外收货及现场证据。
- 运踪：按 PZ 办理整批运踪并同步批内订单，只读轨迹向所有岗位开放，登记权限不随查看权限扩大。
- 财务会计：复核账单和资金申请；出纳登记实际收付款并核销；人事查询和导出报价归属/提成依据。
- 老板：拥有上述岗位的业务办理入口，但执行每个动作时仍遵守同一状态、库存、费用、并发和审计规则，不能通过“老板身份”跳过业务不变量。

## 五、页面与操作体验原则

- 订单中心是单票业务总入口；相关动作尽量在订单内完成，不把用户送到无上下文的外部页面。
- 页面先显示当前节点、缺项、下一办理岗位和可执行动作；只呈现当前可用的主按钮，减少重复和反人类操作。
- 完整委托、费用、货物、责任人和线路信息使用同源数据；审核人员可一次看清，不要求二次录入。
- 日期、选择器、批次和唛头列表必须可直接操作；加载、空状态、失败重试均给出明确反馈。
- 客户只看到自身订单的轨迹和现场照片；内部财务附件与内部异常说明不经客户照片入口泄露。

## 六、实现收口顺序

1. 固化上述四层模型和完成条件，审查所有修改是否违反不变量。
2. 收口录单红字、规则冻结、补录与更正的全部入口及事务竞态。
3. 收口仓储累计、OUL 独占、PZ 分批运输、批次照片与订单聚合完成。
4. 收口双向费用、分摊、账单、收付款、核销和复盘归档。
5. 验证老板单人和岗位协作的拼车/整车四条真实旅程。
6. 在同一稳定源代码上一次性执行全部测试、类型检查、两种构建、数据库新装/升级/重复迁移、浏览器布局与性能对比。
7. 只记录真实通过项和真实遗留项，创建本地回滚提交后停止；本阶段不发布。

## 七、禁止性不变量

- 禁止一批到仓就把整张订单标为运输完成、允许整票提货或归档。
- 禁止同一 OUL 同时占用在两个活动运输批次或装车任务。
- 禁止用直接改订单状态替代真实业务动作、库存、费用或核销。
- 禁止用同名应收顶替必录应付，或用零金额/无往来单位的无效费用绕过门禁。
- 禁止用老板权限、通知链接或隐藏菜单绕过服务端权限和当前节点。
- 禁止投影重试重复写入实物、资金、照片或审计事实。
- 禁止为通过测试删除真实门禁；夹具必须满足生产约束。
