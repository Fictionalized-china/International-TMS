## 3. 性能目标与计量口径

以下为工程验收目标，不是已实现承诺。默认以 10 个同时活跃会话作为第一档容量目标，20 个作为扩展压力档；这是测试假设，不代表已确认的真实客户人数。

| 指标 | 目标与口径 |
| --- | --- |
| 常用订单页 | 在第一档并发下，点击到主要业务资料可见且可操作的 P95 ≤ 1,000 ms |
| 重点范围 | 订单详情当前办理页、完整委托、费用/结算、模块切换；分别统计，不能用快速列表拉低平均值 |
| 普通保存、审批 | 从点击到服务端真实保存完成并呈现最终状态，P95 ≤ 2,000 ms；不先假报成功 |
| 批量业务 | 收货、配载、核销等按数量分档统计，要求结果正确、进度或等待可理解；不硬塞进普通表单指标 |
| 页面刷新协同 | 第一档正常测试负载下，跨浏览器变更可见目标 ≤ 10 秒；不能用延长刷新间隔制造提速 |
| 首次打开 | 新会话/无页面预取独立统计；进程重启后首请求另记，不与连续请求混算 |
| 正确性 | 测试覆盖内无错单、越权、重复扣收款/核销、状态跳过、未保存却报成功；失败请求也计入结果 |

“主要业务资料”至少包含该节点原有的订单信息、状态、阻断原因、费用/审批所需资料、可用操作入口。空白框架、加载动画或尚未加载的审批金额不算可操作。

测量要求：

- 相同环境、账号职责、业务阶段、订单体量及测试客户端做前后比较。记录版本、数据库模式、网络、并发量和样本数。
- 开发比较每场景至少 30 次；最终隔离验收每重点场景至少 100 次，保留原始计时，给出 P50、P95、最大值和失败率。少量样本只称抽样。
- 服务器请求耗时、首字节、响应体完成、浏览器可操作时间、提交后自动刷新分别记录；并行查询累计耗时不等于请求关键路径耗时。
- 分别测试同订单连续读取、不同订单切换、不同账号、多窗口；禁止只测试一个已预热订单。
- 首次打开不要为测量而重启生产服务；进程冷启动在隔离实例测试。
- 并发/业务写入测试用隔离 MySQL 和测试订单，不直接向生产库做压力测试。若隔离环境与生产规格不同，须说明性能外推限制。

## 4. 绝对不能采用的捷径

1. 删除/绕过 `requireSessionUser`、订单授权、字段必填、财务闭环、仓库货齐、费用签核等判断。
2. 全局设置 `syncBusinessWorkflow: false`，或把 `ensureOrderModules`、工作流同步整体注释掉。
3. 把全部同步挪到提交末尾，导致打开快了但保存变得更慢；必须同时测动作总耗时。
4. 用进程级 `Map`、Redis、长 TTL 或共享 CDN 缓存直接复用订单、权限、财务门禁。先完成请求内优化和一致性设计；本计划不新增这些依赖。
5. 把 `transport_orders.updated_at` 当作所有子模块、配置、权限变化的唯一标志，除非已经证明并测试所有写入口都更新它。
6. 只按 SQL 文本去重；参数、组织、订单、账号可见范围、事务及读写阶段不同都可能产生不同结果。
7. 开启 `multipleStatements`、在单个事务连接内无界并行，或把连接池直接放大来掩盖过量查询。
8. 用 `catch { return [] }`、旧数据或默认“通过”掩盖读取、同步和权限错误；失败时仍需正确阻断与可重试提示。
9. 不等待关键数据提交，后台“稍后同步”库存、资金或推进状态后立即报成功；取消请求也不能被当作撤销已提交动作。
10. 为提速缩小业务结果集、少算费用、隐藏当前节点资料、改审批顺序、调整冻结规则或放宽老板之外的账号权限。
11. 通过跳过测试、删断言、扩大时间容差、修改真实订单使门禁通过来完成验收。
12. 全量重装、初始化或种子灌入生产数据库；把用户密码、SQL 参数、Cookie、环境文件加入日志、报告或发布包。

## 5. 执行顺序与批次门槛

执行路线：P0 接管确认 → P1 计量基线 → P2 内网验证 → P3 有限范围查询优化 → 性能复测 → 必要时 P4 同步路径改造 → 必要时 P5 刷新/页面优化 → P6 全流程验收 → P7 发布。

P2 如受实际网络条件限制，不猜测端点、不擅自迁移或购买云资源；记录条件后可继续不依赖它的代码优化。每批有独立回滚节点；出现未解释的业务差异不得继续扩大改造。

### P0：确认起点和保护已有成果

步骤：

1. 检查 Git 状态、当前分支、提交和 `AGENTS.md`；阅读上轮改动，确认不是从旧版本开始。
2. 如准备接触线上，先只读核对实际 `current` 指向、服务状态、数据库版本。旧路径只用于对照，不硬编码成回滚目标。
3. 建立新的进度记录，例如 `docs/reviews/2026-11-09-秒开优化执行记录.md`。逐批追加代码提交、测试结果、计时、未验证项。
4. 记录本批允许修改的文件和预计收益；暂不更改依赖或业务配置。

验收：基线、脏文件和已知限制明确；上轮复用保护测试能够重现。产物：执行记录的起点章节。

### P1：给慢路径建立可关闭的计量，不先猜修法

范围：详情/模块加载器、关键同步服务、MySQL 适配层的必要测量接点。

步骤：

1. 增加测试用或默认关闭的请求级计量，记录阶段耗时、查询次数、读/写数量、可测的连接池等待和重试次数；禁止记录绑定参数、账号凭据和业务正文。
2. 测量覆盖“详情 GET”“委托 GET”“费用 GET”“一次普通提交及其后续刷新”；先在隔离环境执行写入场景。
3. 核对列表和详情的差异，给出最慢的 3 个阶段及其调用次数；需要准确 SQL 统计时区分同形状不同参数，避免伪去重。
4. 对历史测试中仍缺少的角色/客户门户构造隔离夹具。生产有效客户测试账号未知时，只记录限制，不擅自重置账号。
5. 使用同负载比较计量开/关，记录工具自身开销；测试上下文不能跨请求、跨账号串用。

验收：取得新的完整基线，能够解释主要等待；功能输出未改变。不要为了方便计量重写全局数据库执行器。

### P2：独立验证服务器与数据库内网连接

步骤：

1. 核对 ECS/RDS 实际地域、VPC、正式内网端点、白名单及连接要求。不能从公网域名推测替换地址，也不能绑定临时解析 IP。
2. 对现有连接与候选连接做同样的建连和复用连接查询计时，记录失败率；确认访问的是同一目标数据库及一致的模式、数据。
3. 先用隔离候选实例验证连接和应用启动，不带线上定时任务，不改生产连接；保持现有认证与安全要求。
4. 确认改善且环境满足条件后，将连接配置调整作为独立发布步骤，保留原环境配置和恢复方法。与业务代码优化分开计量。
5. 如需数据库迁移、跨区网络、收费资源或账号权限扩展，报告具体缺口，不把这类扩展当作一般性能补丁自动执行。

验收：同库、连接可用、实际往返改善、应用和权限正常、回退可行。没有条件或没有收益则记录并跳过切换。

### P3：只优化一个重点页面的重复查询和无效写入，再扩展

第一票选择 P1 测出的最慢常用页；若相近，优先费用页。不要同时重构所有 loader。

步骤：

1. 列出父详情、嵌入模块及公共服务的读取清单，标明组织、订单、可见范围、参数、依赖和写入边界。
2. 在同一无写入阶段复用完全相同的事实；继续使用上轮 `createOrderWorkflowFieldReader` 和批量加载能力，不另造第二套全局缓存。
3. 将可证明等价的逐项查询改为集合查询，保持排序、空值、重复项、金额精度、授权过滤和返回结构；大 ID 集合分块处理。
4. 对没有状态变化仍写回相同值的语句逐一审查。区分业务时间、同步时间、通知驱动时间；只有证明没有外部语义的无效写入才可减少。不能只按“值相同”删除审计或业务事件。
5. 数据库 `batch` 目前仍逐条执行；需要减少往返时须真正合并安全的语句，或减少调用，不能仅把语句塞进 `batch` 后声称完成。
6. 同一事务内保持顺序和提交保护；事务外仅对独立读做有界并行。慢查询索引仅在执行计划证据支持时加入，并验证 MySQL/D1 迁移兼容性。
7. 前后对比完整数据和每个角色的可见/可办理状态；只允许明确定义且无业务意义的时间等字段规范化，不能过滤金额、节点或责任人差异。

验收：目标场景查询/写入或关键路径耗时确实下降，业务返回等价；其他路径没有明显退化。达到整体目标后仍须 P6/P7，不再为了“架构漂亮”继续大改。

### P4：必要时分离读取与同步——本计划最高风险的一批

仅当 P2/P3 后仍不达标，且 P1 证明工作流同步是主要耗时时进入。本批分为 P4-A 和 P4-B，A 的证据不足时不启用快速读取。

#### P4-A：建立依赖和失效证据，先不改变默认行为

1. 写出“业务事实 → 派生状态 → 写入入口 → 失效机制 → 测试”清单。至少覆盖录单、服务选择、分派、货物、收货、打包、配载、运输/运踪、附件、异常、费用、签核、账单、收付款、核销、复盘、配置修改、版本替换、定时任务及实际存在的导入/修复入口。
2. 每项既要查 service，也要查 action、API、仓库、客户端、脚本等实际写入口。共享配载变动须覆盖关联订单；批量核销须覆盖受影响订单和账单。
3. 区分权威业务数据与可重建的派生状态。不得把资金、仓库实收或签核结果改成可随时重算覆盖的缓存。
4. 选择最小可验证的版本/失效方案；如新增版本字段，采用原子递增和组织/订单范围，不能用秒级时间戳或内存布尔值替代。
5. 业务写入与失效标记必须原子一致，或有可验证的可靠恢复协议；不允许“数据成功写入但标记失败且不可察觉”。
6. 覆盖并发例子：同步读取版本 v，另一事务提交 v+1，同步完成时只能标记 v 已处理，不能把 v+1 覆盖成“已经同步”。用条件更新/现有事务机制保证，并做真实 MySQL 交错执行测试。
7. 权限变化不能只靠订单版本；时间驱动的超时、有效期和预警也不能等业务写入才更新。分别保留实时判断或有明确时限的重算机制。
8. 配置按当前实例的冻结/热更新政策处理，不能“一律读最新模板”，也不能“一律冻结到订单创建时”。

验收：清单每项都有写入口和测试；旧路径仍正常；缺少覆盖的模块继续走旧路径。新字段迁移可重跑且兼容旧应用。先提交这一批，再进入 B。

#### P4-B：只对证明有效的状态启用快速读取

目标行为：

| 情况 | 要求 |
| --- | --- |
| 已同步且依赖未改变 | 读取已持久化结果，保留当前鉴权、时间判断及必要实时门禁 |
| 新订单、旧订单无标记或版本不一致 | 执行原有同步；成功后才记录已处理版本 |
| 同步失败或无法确认有效性 | 不标记成功；保留原来的错误/重试语义，不返回可办理假状态 |
| 同步期间发生新写入 | 新版本仍保持待同步，不能被旧计算覆盖 |
| 提交审批/收货/核销 | 重新校验当前权限、业务状态、余额/货齐条件；读页面的结果不是提交凭证 |
| 不在已覆盖范围的入口 | 保持原流程，不能因“通常不会访问”而删掉校验 |

不得为了请求返回快而将必要同步改为无可靠落地的异步任务。审计/通知执行次数需验证逻辑幂等，既不能重复通知，也不能漏通知。快速路径需有内部开关，关闭后恢复已验证的原语义；不能接受客户端参数控制它。

验收：新旧路径在两个独立、同初始状态的隔离数据集上比较完整业务结果。旧路径有写入，禁止在同一生产请求里双跑进行所谓影子对比。动作总耗时不得因搬运同步而反增，资金与库存门禁仍真实执行。

### P5：必要时减少刷新和页面切换等待

拆成 P5-A 刷新、P5-B 展示两次提交；只做证据支持的部分。

P5-A：

1. 保留焦点恢复、重新可见、同浏览器变更信号，以及跨设备变化发现能力。
2. 可将周期整页重查改为轻量版本检测；检测入口自身必须鉴权，不能泄露其他组织/客户/仓库是否有订单或变化。
3. 版本检测须覆盖相关子模块、共享配载、配置和权限变动；依赖不完整的页面保留旧刷新。列表变化不能只追踪当前打开的某一张订单。
4. 保存成功后立即更新当前页；旧请求返回不能覆盖更新后的状态；提交中的表单和用户未保存输入不能被后台刷新清空。
5. 断网、超时、恢复和检测失败要可恢复；不能标记“已处理版本”后永远不重试。对时间驱动内容仍提供有界刷新。
6. 空闲且数据未变时，不应继续每 10 秒执行一次昂贵的整页同步；跨浏览器可见延迟按第 3 节验证。

P5-B：

1. 只拆可独立加载的附加内容，例如附件预览和已折叠的历史记录；它们仍在原页面原入口可用，并有错误/重试状态。
2. 主管审批所需完整委托、金额、阻断原因及必需附件状态不能留到审批之后加载。不得借机改页面布局、隐藏信息或新增二次录入。
3. 必须先让 GET 安全且代价合理，才评估有限预取；不预取仍会推进工作流的入口，不为每一行订单发起重请求。
4. 任何前端复用都按账号、组织、订单、模块与业务版本隔离；切账号/切仓即失效，服务端授权仍保留。

验收：实际浏览器中的内容、操作、错误恢复和视觉对齐不回退，点击到可操作时间改善；没有用骨架屏时间替代业务就绪时间。

必须覆盖的业务矩阵：

1. 拼车、整车各走通：老板独立办理一条，各岗位协作办理一条；同一初始数据分别运行，不能串用已推进状态。
2. 流程覆盖录单、审核分配、国内运输、收货、打包/适用分支、配载及商务找车、主管确认、仓库出库、运踪、境外收货/提货、费用审批、财务确认、收付款、核销、复盘归档；以订单冻结流程的真实分支为准，不为跑测新增不适用节点。
3. 缺必填资料、资金未核销、货未齐等仍阻断；显式 0 提货费、微小/0 展示体积等既有允许情形不被意外收紧。
4. 业务/操作/主管/客服/财务/出纳各自只拥有正确视图和操作；普通岗位不能继承老板权限；跨组织、跨客户、跨仓库拒绝。
5. 页面打开后撤销权限、改变负责人或修改费用，旧页面提交不能绕过最新校验。
6. 两个账号同时审批；两次重复扫码；同时核销同笔余额；业务变更与同步交错；热更新配置与读取交错；重试后无重复资金、库存、审计和通知副作用。
7. 已完成节点保持历史规则；未完成节点按现有配置机制更新；旧节点重开与版本切换结果正确。
8. 提交回滚、同步失败、数据库短暂不可用、会话过期、断网恢复、快速切单及取消读取后再次进入均可恢复。
9. 仓库搜索保留 `warehouseId`、`itmsTab` 等上下文；403/业务错误不能误判为失效登录而清空会话。
10. 客户端只见所属客户数据，订单/配载运踪与可见附件等原有内容不丢；未知生产客户凭据不能当作登录通过。

自动化要求：SQL/事务行为至少在隔离 MySQL 跑关键场景；SQLite 通过不能证明 MySQL 语义和锁行为。浏览器验收使用正常登录及真实点击，不能只调用 service 再说页面已验收。

最终本地命令，从项目根目录执行：

```powershell
npm run typecheck
npm run test:win
npm run build:mysql
node --check build/server/index.js
node --check production/server.mjs
git diff --check
```

命令必须分别检查退出码；前一条失败不能被后一条成功掩盖。现有 MySQL 验证脚本的测试目标及是否写入须先读脚本确认；不要误用 `db:init:mysql`。类型检查和构建产生的无关文件变动不混入提交。

产物：每重点场景新旧时间、样本数/失败率、业务矩阵结果、测试环境差异、未覆盖项、回滚测试结果。如果未达到 1 秒，只报告实际改善，不改口径宣称达标。

### P7：通过门槛后部署阿里云，并保留回退

1. 再次确认实际旧版本、备份位置、待发布提交及变更清单。网络配置与代码分开记录；不同变量不要一起改后无法定位收益。
2. 使用 `npm run build:mysql` 产物和 `scripts/deploy-alibaba-release.sh`。禁止 `npm run deploy`，它指向 Cloudflare。
3. 发布包只含受版本控制的必要运行/迁移文件、依赖清单和构建产物；不含环境变量、账密、生产快照、测试种子或临时诊断数据。记录 SHA256。
4. 新迁移仅采用向后兼容的增加方式；在隔离环境验证旧应用能读取迁移后的数据库。历史数据没有同步标记时按旧路径处理，不冒充已同步。
5. 使用已有脚本完成备份、核心数据核对、切换和健康检查；新增环境配置需要自己的备份与恢复记录，不能假设脚本会恢复脚本外的修改。
6. 发布后执行老板/岗位/仓库只读巡检，参考 `scripts/verify-boss-dual-mode-readonly.ps1`；从本机已批准账密文件读取，禁止把密码写入报告。
7. 抽样验证公网性能和浏览器实际可操作时间；并行观察错误率、连接池等待、事务冲突和同步异常。生产只做低频检查，完整压力/写入验收留在隔离环境。
8. 客户门户使用有效的授权测试账号验证；若仍缺凭据，在报告标明未验证，不能复用老板身份或篡改客户归属。共享门户路径受到影响而无法取得等效隔离证明时，不放行该部分改动。
9. 记录新旧目录、提交、备份、迁移、检查范围与至少一段观察期数据；停止临时实例和诊断服务，不遗留重复定时任务。

回退条件：出现新越权、金额/库存/节点差异、提交成功但数据未提交、正常入口不可用、持续 5xx，立即停止发布推进并回退；相同条件性能持续变差且无法解释也回退本批。

回退方式：先关闭本批快速路径开关或恢复旧应用/旧连接配置，再验证服务和业务入口。发布脚本的失败回退主要恢复应用，不能把数据库备份自动覆盖回去；覆盖会抹掉发布后的正常业务。若数据已受影响，保留证据并提出精确修复范围，禁止整库盲目恢复。
