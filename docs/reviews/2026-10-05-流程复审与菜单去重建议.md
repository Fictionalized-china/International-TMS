# 会议流程复审与功能入口去重建议

日期：2026-10-05。范围：本地 `feature/modular-order-center`，不是线上验收报告。

## 结论

会议流程的五个开发阶段已进入本地收尾：直接录单、操作主管审核分派、独立每日运踪、商务提前找车、操作主管配载、出境后独立应收应付审批、人事回款与提成报表均有实际服务端实现，不是静态展示。

本轮继续修复了事务门禁、重复提交、热更新和工作总览入口问题。菜单重复主要发生在“同一订单的不同视图”，不等于重复保存订单或费用数据。建议合并入口，不删除业务模块。本报告的菜单方案尚未实施，须项目负责人确认。

没有推送 Git、没有部署云端、没有针对真实订单修节点或改费用。测试订单在临时内存数据库创建，本地持久库仅应用新增结构迁移。

## 本轮发现并修复的问题

| 问题 | 修复方式 | 核验依据 |
| --- | --- | --- |
| 配载生成需要提前分摊成本，旧数据库门禁却要求先出库，形成前后依赖冲突 | 新增专用规划分摊模式：仅同事务中的操作主管规划、已挂载单票、已分配打包任务、未出境且费用未锁定时成立；原出库后门禁继续保留 | `0177_planned_cost_allocation_gates.sql`；完整迁移后的真实双订单配载集成测试 |
| 配载成本预览未保证同步为子订单应付 | 按配置在生成配载同一事务中关联应付费用、分摊行和来源；任一单票锁定则整批回滚 | `planning-cost-integration.server.ts`；双订单费用合计与重复创建测试 |
| 分摊抛重比使用固定值，修改配置可能无效 | 使用现有运营规则的抛重比；默认仍为 1:300 | `loading-batch-planning.server.ts` |
| 录单应付在订单创建后单独写入，失败可能留半成品 | 初始应收、应付随订单创建事务提交；生成失败按来源清理生成数据 | `quote-order.server.ts` |
| 网络重试可能重复开单 | 录单请求按组织、提交人、请求标识去重；绑定内容摘要，变更内容不能冒充原请求；恢复未完成录单重新检查当前职责、客服客户标记、人事紧急开关 | `intake-submission.server.ts` 与定向测试；路由作用域检查 |
| 重复登记或并发登记可能超过已审批付款额度 | 流水请求去重；付款申请额度、流水余额与费用余额在事务内占用和校验 | `settlement-workbench.server.ts`；真实数据库回归 |
| 部分核销重复提交时，尚有余额仍可能再次核销 | 独立核销请求去重，内容变更拒绝；失败重试只恢复派生状态，不重复产生核销明细 | `0179_cash_allocation_idempotency.sql`；部分核销重试测试 |
| MySQL 非严格模式可能将失败的非空事务门禁静默变为零 | 同一事务连接复查门禁实际值，非 1 必须回滚；禁止门禁脱离事务执行 | `mysql-commit-guard.server.test.ts`（模拟原生连接，不是生产实测） |
| 新增结构已列为必需，MySQL 就绪检查的手写查询却可能漏查，导致已迁移仍报缺表 | 必需列和实际查询统一从同一结构清单生成 | `mysql-migrations.test.mjs` |
| 费用模块多次挂载时，可能读到历史首次挂载的规则 | 采用最终费用办理挂载；已通过费用节点保留历史；损坏的冻结绑定拒绝办理而不退回旧默认授权 | `meeting-settlement.server.ts`；冻结工作流测试 |
| 隐藏全部费用审批字段或空字段挂载仍强制旧签核 | 区分旧订单默认链与明确的空配置；无审批链时由本单授权发起人明确确认费用，不新增隐藏必填项 | 隐藏链、空冻结字段回归 |
| 出纳首页无待付款，或点击进入错误结算页签 | 待付款使用结算权限范围，而非普通订单任职范围；快捷入口直接定位收付款页签和申请单 | `meeting-work-overview.server.ts`；实际岗位权限集成测试 |
| 人事报表同名业务员被合并、成本未确认显示为正式成本 | 按账号 ID 汇总；成本、毛利未确认明确标注；提成备注编辑带出旧值 | 人事汇总测试与页面代码审查 |
| 可直接绕过人事列表为未全部回款订单登记提成 | 服务端重复校验应收确认及全部实际核销，不仅依赖列表筛选 | 部分回款拒绝、全部回款允许、版本冲突历史测试 |
| 预警重复发送或停用后仍产生新记录 | 按组织、订单、日期、接收人去重；停用只停止新增，保留历史 | 时效通知真实数据库测试 |

财务回滚保证不等于外部资金已执行：当前系统登记与核销记录不代替真实银行付款。签核和配载的文档生成/状态同步失败保留恢复入口，不以删除已经完成的业务记录解决。

## 重复度判断方式

依据实际菜单定义、路由、业务对象和动作，而不是看到订单列表就判重复。分三个层次：同一对象的相似展示、入口重叠、不同业务对象/责任。这里的高/中/低是产品结构判断，不是未经测量的代码重复百分比。

管理端共定义 24 个入口、5 个菜单分组；具体账号只看到获授权项，不代表每个人看到 24 项。

## 客户端与仓库端

客户端当前 7 项：我的首页、运费试算、我的订单、运输轨迹、账单与文件、通知、账户中心。

- 首页/我的订单/运输轨迹：展示订单有交集，但分别承担摘要、单票操作、时间线。可按会议方向将“我的运踪”作为主入口，内部切订单清单与轨迹；首页只保留摘要和通知。需单独确认，不移除已有唛头、预约、提货能力。
- 运费试算及报价接受：不是本次线下录单主流程必需，建议通过客户门户配置控制显示，而非删除计费和报价能力。
- 账单与文件、通知、账户：各有独立对象和权限，不按“客户只看运踪”直接删除。

仓库端按仓库类型展示：通知、作业总表、验收收货、二次打包贴标、待配载池、创建装车任务、装车与出库、扫码自提、库存盘点、异常处理、仓库库位。

- “创建装车任务”和“装车与出库”已是同一路由的不同视图，可以合成一个装车出库入口下的待创建/执行中页签；动作不是重复。
- 待配载池是仓库货物候选与交接视图，不等于操作主管配载规划。保留时应明确“待交接货物”，不能让仓库重新取得配载规划权。
- 验收、打包、装车、盘点分别改变不同实体，不能因都出现订单号而删掉。

## 待确认的目标结构

日常业务主入口：工作台、订单中心、调度与运踪、配载管理、费用结算、汇总分析。

文件中心和人事专项可按岗位保留快捷入口；业务资料与系统配置使用折叠分组。重要原则：入口精简，原功能不减；默认入口按岗位配置；旧深链接仍有效；移动菜单不自动扩大读写权限；当前业务节点、数据、费用和历史均不因菜单移动改变。

确认后才进行菜单/页签重组和客户端、仓库端的可选入口调整。此次仅修业务 bug 和整理建议，没有实施菜单去重方案。
