# 纯 UI 四单全流程测试设计（1 整车 + 3 拼车组成 1 个 PZ）

> 当前状态：**测试框架与用例骨架已完成，尚未据此宣称全流程通过。** 只有使用全新 attempt、新客户和新订单从头走到复盘归档，才可形成最终验收结论。

## 1. 方法与目标

本设计按用户指定的[软件测试流程方法参考](https://blog.csdn.net/IGGIRing/article/details/106093982)组织：先做需求与约束分析，再定义范围、角色、环境、策略、用例字段、执行证据、缺陷闭环和最终报告。

每个自动化用例都必须记录：

- 用例 ID、标题、优先级、类型和业务阶段；
- 前置条件、输入、角色、站点、页面前后地址；
- 可见键鼠动作、预期结果、实际结果和错误；
- 预期门禁来源、配置模式、UI 表现、服务端表现和责任岗位；
- 步骤截图、角色 trace、动作数、跳转数与认知事件。

测试目标不是“脚本跑完”，而是证明各岗位用最少行为和最少思考即可协同完成完整业务，同时无越权、无死循环、无状态不同步。

## 2. 不可破坏约束

1. 所有业务数据只能通过浏览器可见页面和键鼠动作创建、修改和推进。
2. 禁止直接读写 D1/SQLite，禁止 SQL、HTTP/API 捷径、`page.evaluate`、DOM/存储注入、`set_input_files`、网络响应伪造和 `force` 穿透。
3. 正向业务只能从登录页、菜单、列表和页面“下一步”进入；深链仅用于有明确原因记录的负向门禁验证。
4. 每个账号使用独立浏览器 context，不共享 Cookie 或 storage state。
5. 凭据只能由运行时秘密文件或环境变量载入；仓库文件、JSON 日志、终端结果不写邮箱和密码。截图遮罩登录标识，trace 不采集 DOM 快照或页面截图。
6. 发现阻断或逻辑缺陷后，本 attempt 立即标记失败/阻塞。修复后必须生成新 attempt、新客户、新报价和新订单，从客户建档重新开始，不续用旧单据冒充完整通过。

## 3. 门禁唯一来源原则

业务门禁、UI 必填标识、提示语、办理按钮和模块完成状态必须共同读取订单的工作流实例配置：

| 配置模式 | 页面 | 服务端 | 是否阻断 |
| --- | --- | --- | --- |
| 必填 `required` | 显示字段、责任人和清晰缺口 | 缺值拒绝，齐全后允许 | 是 |
| 选填 `optional` | 显示可办理入口但不标必填 | 可保存，也可不填推进 | 否 |
| 隐藏 `hidden` | 不渲染控件、按钮和红色提示 | 拒绝该字段对应动作 | 否 |
| 只读 `read_only` | 仅显示状态/历史，无伪操作按钮 | 拒绝修改 | 否 |

岗位权限配置只回答“谁能看、谁能办、数据范围是什么”；它不能代替工作流配置决定业务资料是否必填。系统唯一性、幂等和扫码归属属于不可配置的完整性约束，必须在用例中单独标明，不能伪装成工作流门禁。

## 4. 范围与角色

### 范围内

- 18 个测试账号的分站点登录和菜单可见性；
- 全新客户、联系人、地址；
- 1 张整车报价、3 张拼车报价及客户确认；
- 委托补充、审批、普通订单负责人分配；
- 国内运输、国内仓扫码入库；
- 整车独立装车出库；
- 三张拼车生成一个 PZ、主管整批重新分配、整批装车出库；
- 逐票报关放行、整车/PZ 运踪；
- 境外仓扫码入库、客户预约、仓库扫码交付签收；
- 客服、业务、财务、出纳协同结算；
- 完成复盘、异常处理和归档；
- 权限越权、错误/重复扫码、重复确认、缺必填值、未放行出境、动态配置同步等防呆用例。

### 范围外

- 用数据库或接口批量造业务状态；
- 把历史订单续跑结果算作本轮完整通过；
- 性能压测、灾备切换和生产环境发布；
- 自动修改正式账号密码或权限配置。

### 主要责任岗位

业务岗、业务主管、操作主管、操作岗、单证岗、客服岗、财务会计岗、出纳岗、国内仓、境外仓和客户门户用户。开发者账号只用于验证工作流字段模式动态同步，并在用例结束时恢复原配置。

## 5. 主线与用例资产

主线顺序：

`客户建档 → 四份报价 → 客户确认 → 委托补充 → 委托审批 → 任务分配 → 国内运输 → 国内仓入库 → 整车装车 / 三票组 PZ → 报关放行 → 实际出境及运踪 → 境外仓入库 → 预约与签收 → 三方结算 → 复盘归档`

机器可校验用例资产位于：

- `tests/e2e/tms_full_flow_blueprint.py`：33 个用例，包含 26 个主线、4 个防呆、2 个负向门禁和 1 个前置冒烟；状态固定为 `PLANNED_NOT_EXECUTED`，不会把设计稿冒充执行结果。
- `tests/e2e/tms_multi_account_smoke.py`：18 账号登录与菜单可见性冒烟，可先按角色子集运行。
- `tests/e2e/tms_ui_harness.py`：多 context、步骤/门禁/证据日志、trace、动作计数和 fresh-attempt 台账。
- `tests/e2e/tms_ui_credentials.py`：运行时凭据解析与脱敏。
- `tests/e2e/ui_only_guard.py`：静态阻断数据库、接口、DOM 注入、原始 Playwright 写操作等捷径。

## 6. 预检与执行方式

先执行框架自检：

```powershell
python -m unittest discover -s tests/e2e -p 'test_*.py' -v
python tests/e2e/ui_only_guard.py tests/e2e/tms_multi_account_smoke.py tests/e2e/tms_full_flow_blueprint.py --json
```

凭据文件只在当前终端指定，不写入仓库：

```powershell
$env:TMS_E2E_CREDENTIALS_FILE = '<本机秘密文件路径>'
python tests/e2e/tms_multi_account_smoke.py --roles sales,operation_supervisor,operation,document,finance,cashier,domestic_warehouse,overseas_warehouse,customer --headless
```

子集通过后，不带 `--roles` 执行 18 账号完整冒烟。冒烟通过才开始全新四单主线。

## 7. 结果与缺陷闭环

- `passed`：实际页面、权限、状态和后续影响均符合预期；
- `failed`：已有入口但行为或结果不符合预期；
- `blocked`：正常业务入口缺失或形成循环，无法继续；
- `planned`：只有用例设计，没有执行证据，不计入通过率。

每次失败保留摘要、脱敏截图、角色 trace、页面文本和动作指标；代码修复后关闭旧 attempt，创建新 attempt，从新客户开始。最终报告必须区分“静态/单元验证”“本地真实 UI 验证”和“生产环境证明”，并逐条列出实际遇到的门禁及其配置来源。
